Data pour la finance : bases de données, SQL, DSA, KDB+/Q

Comment stocker, interroger et structurer efficacement des données financières, y compris à haute fréquence.

Complexité algorithmique O(1) accès direct  <  O(log n) recherche triée  <  O(n) parcours simple  <  O(n²) comparaison par paires

Bases de données relationnelles

  • Organisent la donnée en tables reliées par des clés (primary/foreign key).
  • Garantissent l'intégrité des données via des contraintes.
  • Standard pour les données transactionnelles (positions, ordres, contreparties).

SQL

  • Langage universel pour interroger et manipuler les bases relationnelles.
  • SELECT / JOIN / GROUP BY : les 3 briques à maîtriser en priorité.
  • Compétence attendue quasi partout en finance quantitative.

DSA (structures de données)

  • Listes, arbres, hashmaps, files : le choix de structure impacte directement la performance.
  • Un carnet d'ordres est souvent modélisé avec des arbres ou des files triées.
  • Essentiel pour tout système de trading à faible latence.

KDB+/Q

  • Base de données colonne spécialisée dans les séries temporelles à très haute fréquence.
  • Utilisée par les desks de trading haute fréquence pour stocker et interroger le tick data.
  • Le langage Q est réputé difficile mais extrêmement performant sur ce cas d'usage.

Qui utilise quoi ?

Data engineer Conçoit et maintient les pipelines et bases de données de l'organisation.
Quant developer Utilise DSA pour optimiser la performance des moteurs de pricing/risque.
Analyste Interroge les données via SQL pour produire des analyses et reportings.
Trader haute fréquence S'appuie sur KDB+/Q pour analyser le tick data en temps quasi réel.

À retenir

  1. SQL reste la compétence data la plus universellement utile en finance, avant tout langage de programmation spécifique.
  2. Le choix de structure de données (DSA) devient critique dès que la latence ou le volume de données augmente fortement.
  3. KDB+/Q n'a de sens que pour des volumes de données tick-by-tick très importants — inutile pour un reporting mensuel classique.

Exemples concrets

Requête SQL

Extraire l'historique de prix d'un titre sur 5 ans avec un simple SELECT ... WHERE ... ORDER BY date.

Table KDB pour tick data

Stocker des millions de trades par jour et calculer un VWAP en quelques millisecondes grâce au stockage colonne de KDB+.

Hashmap pour lookup

Associer un identifiant d'instrument à ses caractéristiques en accès instantané O(1) plutôt qu'en parcourant une liste.

Arbre pour un carnet d'ordres

Un carnet d'ordres est souvent implémenté avec un arbre équilibré pour retrouver rapidement le meilleur prix d'achat/vente.
